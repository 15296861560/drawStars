## 一、需求背景与目标

### 1.1 背景

drawStars 平台已具备完整的内容测评能力：PC 管理端可创建带评分模式与结果反馈的问卷（下文统称「测评」），C 端提供免登录直达的 H5 填写页（`/survey/fill/:shareCode`）与结果页（`/survey/result/:responseId`），答卷已支持 `source` 来源字段与多渠道分发链接。

平台同时运营微信公众号输出周易与心智模型内容，但公众号与测评之间目前是断裂的链路：

- **入口断裂**：公众号文章、关键词回复、关注欢迎语中无法生成「带来源标识」的测评链接，运营人工拼链、无统一记录；用户点开链接后也没有一个集中的「可测什么」的页面；
- **回流断裂**：测评结果页/完成页没有关注公众号的引导位，测评流量无法沉淀为公众号粉丝；
- **注册断裂**：游客免登录完成测评后即流失，没有「点链接后快速注册」的低门槛通道，答卷无法归属到账号；
- **激励断裂**：完成测评、生成海报、新用户注册等关键行为没有积分激励，与平台已有的积分管理体系互不相通；
- **数据断裂**：`survey_response.source` 字段虽存在，但缺少渠道级进入/点击/完成/注册/引导交互的事件记录，无法回答「哪个渠道带来的用户完成率最高、注册转化与回流效果如何」。

**现状量化基线**（编制时按公众号后台与答卷库估测，上线前由运营按实值复核替换，此后以看板事件流为准）：针对经公众号入口进入 H5 的微信用户（用户），在阅读文章、回复关键词、关注公众号并点击链接进入测评的场景（场景），因入口无统一带参链接、报告页无关注引导、游客答卷无法归户、关键行为无积分激励（问题）——公众号粉丝仅 200 余人且大部分低活跃（估测常读/互动占比不足三成，以后台「常读用户」口径复核）、月均净增关注仅个位数（估测）、图文篇均阅读为两位数量级且「阅读原文」点击率不足 2%；H5 测评月均完成仅数十份，其中游客提交占比约 85%、游客注册转化率不足 2%（月均沉淀注册用户不足 1 人），流量在「完成即流失」断点损耗约 98%，且公众号侧无法归因任何一次转化（量化数据）。

本 PRD 规划在现有前后端架构上做**增量拓展**：前端在 drawStars-Vue3 中扩展公开免登录的「问星」H5 产品线；后端在 drawStars-serve-node 新增 `assessment`（心智测评）模块，串联「公众号内容引流 → 问星广场 → 测评 → 报告 → 快捷注册 → 积分激励 → 分享回流」的完整闭环。

### 1.3 公众号账号能力边界（决定 v1.0 技术选型）

当前公众号为**个人未认证订阅号**，各能力可用性如下，v1.0 的全部功能均只依赖「无限制」档能力：

| 能力 | 可用性 | 对本需求的影响 |
| ---- | ---- | ---- |
| 文章发布 + 阅读原文链接 | ✅ 无限制 | 文章 → 问星主入口（正文超链受限，仅「阅读原文」可外链） |
| 关键词自动回复（后台配置） | ✅ 无限制 | 关键词 → 问星入口（v1.0 走公众号后台原生配置） |
| 被关注回复欢迎语 | ✅ 无限制 | 欢迎语 → 问星入口（同上） |
| 自定义菜单 | ⚠️ 有限 | 一级/子菜单的动作仅可「发送消息」，不可「跳转网页」；改动后 24h 内生效 |
| OAuth 网页授权 / 模板消息 / 带参数二维码 / JS-SDK 高级接口 | ❌ 受限 | v1.2+ 认证后启用（仅做架构预留） |

因此 v1.0 的定位是：**系统侧做「类型库 + 上架选品 + 配置仓库 + 链接工厂 + 引导位 + 埋点与积分」；公众号侧靠后台原生配置人工承接**。系统对公众号 API 的服务端对接（access_token、回调）规划在 v1.1。

### 1.4 设计目标

| 目标 | 说明 |
| ---- | ---- |
| **可直达** | 问星 H5 免登录、独立域名可直接访问，微信内置浏览器打开无阻断；广场页回答「能测什么」 |
| **可归因** | 全部入口链接统一由系统生成，携带 `source/refId/sessionId` 参数，进入即记录事件流；填、完、注册、分享全链路埋点齐全 |
| **可回流** | 报告页、完成页、分享海报三处标准化关注引导位，长按二维码即可关注 |
| **可激励** | 完成测评 / 生成海报 / 新用户快捷注册三类行为对接积分规则，幂等发分不超发 |
| **可转化** | 手机号 + 验证码一键「注册即登录」，游客答卷随注册迁移归户，注册零流失 |
| **可运营** | 关键词/欢迎语/菜单文案在管理端集中维护 + 公众号后台操作 SOP，一键复制粘贴、状态标记可追踪 |
| **可度量** | 渠道进入 → 广场点击 → 测评完成 → 注册 → 积分 → 分享的六级漏斗看板，按 source 细分 |
| **可升级（预留）** | 公众号能力以策略模式预留 Provider 与消息处理器注册表，账号认证升级后免改核心流程 |

#### 1.4.1 量化目标（SMART）

目标期限：自 v1.0 灰度转全量日（T0，见 8.2 R3）起 90 天；基线为 1.1 节量化口径：

| # | 指标 | 口径（以 4.7 看板为准） | 基线（估测） | 目标值 |
| - | ---- | ---- | ---- | ---- |
| G1 | 渠道→完成转化率 | L3/L1（E03 量 / E01 三元组去重量，4.7.1） | 无归因度量 | ≥ 15% |
| G2 | 游客注册转化率 | L5/L4（E05 isNewUser=true / E04，4.7.2） | < 2% | ≥ 8% |
| G3 | 公众号净增关注 | 公众号后台「用户增长」（「常读用户」占比作活跃度辅助口径），S6 月度人工核对 | 粉丝 ≈ 200 人且低活跃，月净增个位数（估测） | T0+90d 累计净增 ≥ 300 人（总量翻倍以上） |
| G4 | 「每日智慧」打卡完成量 | E03 按 quick_daily 类型下钻计数 | ≈ 0（未上架） | 月均 ≥ 200 份（日均约 7，依赖分享回流放大） |
| G5 | 积分漏发率 | 1 − 注册→领分率（4.7.2） | 无度量 | ≤ 1% |

- 北极星指标：**周完成测评人数**（E03 按周去重）；护栏指标：单 session 异常事件率 ≤ 1%、人均日积分获取不超 4.8.1 限额设计值。

#### 1.4.2 达成路径（量化目标 ← 功能拆解）

| 量化目标 | 承载功能（PRD 章节） | 作用机理 |
| ---- | ---- | ---- |
| G1 完成转化 ≥ 15% | 渠道链接工厂（4.4.2）+ 广场选品（4.3.1）+ 免登录填写（4.3.2/4.3.3） | 带参直达链降低跳失；广场聚合「能测什么」降低选择成本；免登录零阻断完成 |
| G2 注册转化 ≥ 8% | QuickRegisterSheet + claim 归属迁移（4.3.5）+ REGISTER_WELCOME 20 分（4.8.1） | 30 秒注册即登录；完成态后置触发不打断；注册即兑现激励 |
| G3 净增关注 ≥ 300 | 引导位配置（4.4.1）+ 报告/完成页/海报三触点（4.2.2/4.3.4）+ 欢迎语与关键词 SOP（4.5.2/4.5.3） | 在关注动机最强的结果场景放二维码；海报双码促二级传播 |
| G4 打卡月均 ≥ 200 | quick_daily 种子模板（4.1.1）+ daily 关键词规则（4.5.3） | 1 分钟低门槛形成每日回访心智 |
| G5 漏发率 ≤ 1% | grant 幂等 + 唯一索引（4.8.2）+ 注册→领分率看板（4.7.2） | 唯一约束去重；漏发数据自动暴露闭环 |

里程碑拆解：v1.0 灰度上线（R1–R2，跑通链路、校准口径）→ R3 全量并交付看板（T0）→ T0+30d 覆核 G1–G5 趋势 → T0+90d 验收，未达标项按 source/漏斗层下钻归因，进入 v1.1 复盘。

#### 1.4.3 评估方式与时间窗

| 项 | 约定 |
| ---- | ---- |
| 评估方法 | 一律以问星数据看板（4.7.1 七级漏斗 + 4.7.2 指标）为准，口径公式不另行定义；G3 公众号侧数据以后台「用户增长」人工核对并记入看板下钻抽屉 manual_note（S6） |
| 评估频率 | 周度漏斗复盘（运营例会）；月度积分流水对账与漏发率核对 |
| 评估时间窗 | T0 = 灰度转全量日（8.2 R3）；T0+30d 中期覆核；T0+90d 验收判定 |
| 达成判定 | G1/G2/G5 达标即核心目标达成；G3/G4 达成率 ≥ 80% 视为达标（公众号侧存在不可控折让）；未达标项进入 v1.1 归因复盘与迭代 |

### 1.5 不在本期范围

- 公众号服务端 API 对接（access_token 托管、服务器回调、被动回复接口、素材管理）→ **v1.1**
- OAuth 网页授权（获取 OpenID、测评记录与粉丝身份绑定）→ **v1.2+，需账号认证**
- 模板消息/订阅通知推送 → **v1.2+，需认证服务号**
- 带参数二维码（区分渠道的扫码关注）→ **v1.2+**
- JS-SDK 高级接口（自定义分享卡片、H5 内直接关注组件）→ **v1.2+**
- 匿名「免任何输入自动建号」：游客静默生成账号的方案不采用（垃圾号风险 + 现有建号体系无先例），v1.0 以「手机号+验证码快捷注册」替代；OAuth 静默授权归 v1.2+
- AI 出题上线（v1.0 题目生成走模板复制 + 空白创建两条路径，AI 生成仅做 v1.1 挂接设计）
- 测评本身的新题型扩展（归 survey 模块，见《问卷管理系统_PRD_v1.0.md》）
- 公众号内容素材管理（文章编辑、发布排期）

## 二、用户角色

| 角色 | 说明 | 核心诉求 |
| ---- | ---- | ---- |
| **平台管理员** | 拥有全部权限（`super_admin` 直通），管理心智测评中心全部配置与数据 | 全局配置管控、数据审计、积分发放质量 |
| **运营人员** | 维护测评上架、文案引导位、渠道入口、回复规则，跟进问星看板与公众号后台配置 | 选品上架高效、文案拿来即用、转化数据直观 |
| **H5 游客（微信用户）** | 无平台账号的公众号粉丝/被分享者，免登录使用问星 H5 | 打开即测、结果可看、注册一键完成 |
| **注册用户** | 平台已有账号，完整体验测评并沉淀积分与记录 | 答卷归属账号、积分到账可查、与游客一致的引导体验 |

> 权限码遵循现有 RBAC 体系（模块:资源:动作），本模块归属 `assessment` 域：菜单可见性走 `assessment:oa:list / assessment:channel:list / assessment:reply:list / assessment:info:list / assessment:stats:view`；按钮级操作走 `assessment:oa:manage / assessment:channel:manage / assessment:reply:manage / assessment:info:manage`。`super_admin` 不受权限码限制。问星 H5 三页与事件上报接口全部 `@Public()` 免登录；快捷注册复用登录域 `loginApi`。

## 四、各模块详细设计

### 4.1 测评类型库与测评创建

> 回答两个问题：**「可测评什么」（类型库）**与**「评测题目从哪来」（生成路径）**。测评本质仍是 survey 域问卷（创建、赋分、规则引擎、结果反馈全部复用现有能力，见 4.1.3），本模块在其上补「类型库定义 + 上架选品」两层。

#### 4.1.1 测评类型库（可测什么）

类型库 = 平台规划的经营品类目录，决定广场分类、预置模板与判定模型的选择。**一个类型可上架多个测评（同题量/不同主题），一个测评只属一个类型**。

| 类型代码 | 类型名 | 判定模型（见 4.2.1） | 建议题量 | 建议时长 | 版本 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `archetype` | 周易心智原型 | 类型判定（M1，取最高维度为结果原型） | 30 题 | 约 8 分钟 | **v1.0 首发** |
| `emotion` | 情绪能量 | 维度画像（M2，数值区间多维展示） | 15 题 | 约 4 分钟 | **v1.0 首发** |
| `quick_daily` | 每日心智打卡 | 分档判级（M0，对应蓝本「每日智慧」轻测评） | 1～3 题 | 约 1 分钟 | **v1.0 首发** |
| `cognition` | 认知风格 | 类型判定 | 22 题 | 约 6 分钟 | v1.1 |
| `relationship` | 关系模式 | 维度画像 | 25 题 | 约 7 分钟 | v1.1 |
| `decision` | 决策风格 | 类型判定 | 18 题 | 约 5 分钟 | v1.1 |
| `stress` | 压力应对 | 分档判级 + 维度画像 | 20 题 | 约 5 分钟 | v1.1 |
| `motivation` | 职业驱动力 | 维度画像 | 28 题 | 约 8 分钟 | v1.1 |
| `learning` | 学习风格（VARK） | 类型判定 | 16 题 | 约 4 分钟 | v1.2 |
| `team` | 团队角色（贝尔宾九角色） | 类型判定 | 30 题 | 约 8 分钟 | v1.2 |

**类型库种子机制**：

- 类型目录以常量枚举（前端 `src/constants/assessment.ts` + 后端类型定义）维护，不单独建表；`assessment_info.category` 引用枚举值；
- 每个首发类型随版本内置 1 个**预置问卷模板**（含题目、赋分、grade_MAPPING/dimension 规则与结果反馈文案），以 survey 模板管理（4.6.1）的形式种子下发，运营可复制微调；
- 后续新增类型 = 前后端同步注册枚举 + 下发预置模板 + 广场自动出现新分类 Tab，属配置级扩展，不改核心流程（见 9.1）。

#### 4.1.2 测评题目生成（三路径）

| 路径 | 操作方式 | 产出与去向 | 版本 |
| ---- | ---- | ---- | ---- |
| **A 模板复制（主路径）** | 问卷管理中复制类型库预置模板 → 得到新问卷草稿 → 微调题干/选项/赋分 → 发布 | 新问卷（survey 域，published 后可上架） | v1.0 |
| **B 空白创建 + 题库引用** | 空白新建问卷；从**个人题库**（survey 4.6.2，标签/关键词搜索）逐题引用或全量导入；再按 4.1.3 完成赋分与规则配置 | 新问卷 | v1.0 |
| **C AI 辅助生成** | 输入：类型 + 主题 + 题数 + 风格描述 → AI 产出题目**草案**（JSON 对齐 question/option/赋分结构） → 运营**人工审核**（可改可删可加入题库） → 审核通过后走路径 B 的题库引用流程组装 | 题库素材（不直接上架，杜绝 AI 未审内容直达 C 端） | v1.1+ |

**路径选择规则**：

```text
需要快速上新标准类型      → A（复制官方预置模板，改主题文案即可）
需要差异化原创内容        → B（题库积累 + 空白组装）
需要批量扩产同类型题目    → C（AI 生成草案 → 审核入库 → B 组装）
```

> 题目 `question.config.scoring` 赋分与规则配置的具体规则（单选固定分/多选部分给分/填空精确匹配、及格分 60%、重考取最高分等）全部沿用问卷管理现状，本文不重复定义，边界见 4.1.3。

#### 4.1.3 复用问卷管理能力边界矩阵

| 问卷域能力 | survey 现状 | 心智测评系统的使用方式 |
| ---- | ---- | ---- |

| 题目赋分 | 已实现：`question.config.scoring`（单选固定分、多选全对满分/漏选半分/错选 0 分、填空精确匹配/正则） | 直接复用 |

#### 4.1.4 测评上架管理（问星广场选品，`assessment_info`）

「上架」= 把 survey 域已发布问卷包装成问星广场商品，附加运营信息：

| 功能 | 说明 |
| ---- | ---- |
| 上架列表 | 管理端网格/表格展示：类型、绑定问卷短码、标题、推荐语、角标、状态（上架/下线）、排序权重、贡献数据（PV/完成数快照，取埋点统计） |
| 新建上架 | 选择已发布问卷 → 显示校验结果（见下） → 填类型分类 / 一句话推荐语 / 广场封面图 / 角标（HOT、NEW、限免）/ 排序权重 → 首页/广场可见 |
| 上架校验（publish/unpublish 前置，共四项） | ① published：问卷必须为 published 态；② 类型注册：type_key 必须在 4.1.1 类型库注册表白名单内（未注册拒绝保存，见 5.2.4）；③ 规则对应：绑类型为 archetype/decision/cognition/learning/team（类型判定类）时校验问卷 `settings.scoring_rules` 含 dimension 规则，绑 emotion/relationship/stress（画像类）时校验含 dimension 规则，quick_daily 校验含 grade_mapping；④ 展示信息：question_num > 0 且与问卷实际题数一致（上架快照，5.2.4）。四项任一失败给阻断提示与规则示例 |
| 编辑信息 | 修改推荐语/封面/角标/排序即时生效，不触碰问卷本体内容 |
| 下线 | 状态置 off；广场即刻隐藏，已生成并散播出去的链接仍可访问填写（链接由 shareCode 决定，同现有语义）；下线提示文案「测评已下架的时间点与历史数据保留」 |
| 删除 | 仅删除上架记录；问卷本体走问卷管理删除流程；删除前置校验存在进行中的数据则仅允许下线 |

> 广场排序规则：置顶（sort 权重）> 上架时间倒序；角标仅作视觉标签不参与排序。

#### 4.1.5 AI 辅助出题（v1.1+ 挂 ai-assistant）

- 入口放在心智测评中心「测评创建」页签内的「AI 出题」按钮；
- 输入约束：不多于 50 字的风格主题描述 + 类型枚举 + 题数上限 30 题 + 难度低/中/高；
- 输出为题目草案列表（对齐 survey 题目 JSON：题干/选项/赋分/维度标签），状态标记 `draft`；一次生成限 20 题，仅入「待审核」区；
- **硬规则：草案必须人工逐题审核，审核通过的题目仅可入题库或模板，不提供「直接上架」通道**；AI 无积分、无埋点，纯管理端工具。

### 4.2 测评分析与报告

> 回答第三个问题：**「怎么进行分析测评」**。判定全部构建在 survey 规则引擎的现有 5 类规则之上（weight/bonus/penalty/grade_mapping/dimension），**本 PRD 不修改规则引擎**，只约定「类型库三类测评分别用哪种规则组合、结果如何呈现」。

#### 4.2.1 三类计分判定模型

**通用前序**：提交答卷 → 自动判分（评估开启自动/混合判分）→ 规则引擎按序执行 `weight 加权 → bonus/penalty 调整 → grade_mapping / dimension 计算` → 结果反馈渲染落库（`survey_response` 携带 totalScore、gradeLabel、明细）。

**M0 分档判级（grade_mapping）**

| 项 | 规则 |
| ---- | ---- |
| 适用类型 | `quick_daily` 每日心智打卡、`stress` 压力应对（等分数向测评） |
| 规则配置 | `scoring_rules` 中配置 `grade_mapping.ranges:[{min, max, label, color}]`，区间闭开自定（如 0-39 低能量/40-69 中等/70-100 高能量） |
| 结果呈现 | 单一等级标签 + 颜色 + 该等级解读文案（自定义文本反馈），如「今日能量档：高能量 🔥」 |

**M1 类型判定（dimension + 取最高维度）**

| 项 | 规则 |
| ---- | ---- |
| 适用类型 | `archetype` 周易心智原型、`cognition`、`decision`、`learning`、`team`（离散类型向测评） |
| 规则配置 | 每题选项赋分挂到维度（`dimension` 规则，如「乾天: Q1+Q2+Q6 平均分」「坤地: Q3+Q5 平均分」…），测评 N 型即配 N 个维度 |
| 判定算法 | 各维度聚合得分 → **取最高分维度为用户的结果类型**；多个维度同分并列最高时，输出并列维度组合并提示「混合型倾向」 |
| 实现位置 | **现有规则引擎只产出各维度分数，不含「取最高」逻辑**——该判定在问星报告页做**前端增强**：报告页读取维度分数数组后计算最高维度渲染主结果；此为已对齐代码事实的设计决策，后端零改动（结果不落库 gradeLabel 的场景以渲染分数组为准） |
| 结果呈现 | 「你的周易心智原型是：乾天型」+ 各维度得分占比条 + 类型专属解读文案（写在维度 label 描述中） |

**M2 维度画像（dimension + 参考区间）**

| 项 | 规则 |
| ---- | ---- |
| 适用类型 | `emotion` 情绪能量、`relationship`、`motivation`（剖面画像向测评） |
| 规则配置 | 若干 dimension 维度（如情绪能量：平静/喜悦/焦虑/倦怠 四维），每维度可配参考区间文案 |
| 结果呈现 | 各维度得分**条形图**对比 + 每维度一句解读；突出显示得分最高/最低维度；雷达图多维呈现标注 `v1.1+` |

**M1 规则配置示例（archetype，节选）**：

```json
{
  "rules": [
    { "type": "dimension", "name": "乾天型", "expression": "乾天: Q1+Q2+Q6 的平均分" },
    { "type": "dimension", "name": "坤地型", "expression": "坤地: Q3+Q5 的平均分" },
    { "type": "dimension", "name": "坎水型", "expression": "坎水: Q4+Q7+Q9 的平均分" }
  ],
  "feedback": {
    "mode": "custom",
    "text": "你的周易心智原型是：{gradeLabel}",
    "showAnalysis": false
  }
}
```

现有代码事实：路由已是顶层 `meta.public: true` 路由（App.vue 守卫白名单放行），`getFill(shareCode, params.source)` 已支持 source 透传，匿名提交 `POST /survey/:id/response` 已支持 `source/deviceInfo/deviceFingerprint`——本节为增量改造，不新增路由。

**进入承接规则**：

```text
1. 页面挂载时解析 URL query：source、refId、sessionId
2. sessionId：query 已带（分享链接回访）直接沿用；否则生成 32 位随机串，
   写入 sessionStorage（key: assessment_session_id），生命周期为当前浏览器会话
3. 若 source 存在 → 上报事件 { event_type: channel_visit, source, ref_id, session_id, share_code }
4. 同三元组（session_id + source + ref_id）5 分钟窗口内重复进入不重复上报
   （前端节流 + 后端去重双保险）
5. 无 source 的自然流量：不强制上报；sessionId 照常生成（供后续事件挂载）
```

**答题与提交联动**：

```text
提交成功后（现有 submitted 完成态渲染前）：
1. 提交 body 携带 sessionStorage 中的 source/refId（refId 为本期补齐的透传约定）
2. 上报 { event_type: response_complete, source, ref_id, session_id, share_code,
         response_id }（response_id 取提交接口返回值）
3. 游客身份的 response_id 写入 sessionStorage 待迁移池
   （key: pending_response_ids，数组，供 4.3.5 注册后 claim）
4. 渲染完成态：提交结果反馈 + 问星 CTA 区
```

**完成态 CTA 区布局（`submitted=true` 时展示）**：

```text
✅ 测评已完成！
[查看完整报告]      → 跳 /survey/result/:responseId（不变）
关注「{公众号名称}」获取完整解读   ← OaFollowGuide(position=complete)
游客：[注册保存这份报告 + 领新人积分]  ← 触发 QuickRegisterSheet（4.3.5）
游客：完成态无论是否注册，报告页链接长期有效（公开路由）
```

**填写期不打断原则**：答题过程中不弹任何注册/关注弹层；关注引导与注册 CTA 仅出现在完成态之后。`guide_enabled=false` 或 guide 接口异常时引导位**静默隐藏**——治理原则：不弹错、不占位、不阻断测评主流程。

#### 4.3.5 快捷注册与答卷归属迁移（「点链接后快速自动注册」）

**设计决策（不做匿名自动建号）**：游客点开链接后不静默生成账号。原因：现有建号体系（`registerByPhone`/`registerByOauth`）均要求身份输入，无匿名建号先例；且匿名号无法防刷积分、产生大量垃圾账号。v1.0 采用**「手机号 + 验证码，一键注册即登录」**方案——30 秒内完成，注册成功后游客期答卷与积分全部自动归属。

**① QuickRegisterSheet 注册弹层（组件，不新增路由）**

| 触发位 | 文案（默认，可配置） |
| ---- | ---- |
| 报告页游客浮条 | 「注册保存这份报告 · 新人 +20 积分」 |
| 填写完成页 CTA | 「注册保存报告 + 领取积分」 |
| 广场右上角登录/注册入口 | 「登录/注册」 |

弹层内容：手机号输入 + 短信验证码（60 秒重发倒计时，复用现有登录验证码 `captcha` 接口，Redis 120s TTL）+ 可选昵称；提交即 `POST /loginApi/quickRegister`。弹层每次展示上报 `register_show`（E04）。

**② 后端 quickRegister（注册即登录，新增登录域接口）**

```text
POST /loginApi/quickRegister   body: { phone, captcha, nickname? }
处理流程（对齐现有 AuthService.registerByPhone → userService.registerByPhone → setToken 范式）：
1. 强校验短信验证码：captcha 与 Redis 记录匹配，校验后立即删除（一次性消费）
2. 按 phone 查用户：
   a. 已存在 → 等同登录，直接 setToken 下发 token（不影响既有密码登录）
   b. 不存在 → registerByPhone 建号范式：
      · 昵称：入参 nickname，缺省「星友」+ 4 位随机后缀
      · 密码：随机串（用户不在注册时设置；首次登录后可「忘记密码」流程找回/修改）
      · 建号 → setToken → seed-rbac 按 level 补绑基础角色（沿用现有机制）
3. 返回 { token, isNewUser: true/false, user: { id, name, phone } }
安全约束：quickRegister 通道验证码不通过即 400，不存在「免验证码注册」旁路；
captcha 校验一次性消费为**现状整改项**（现有 verifyCaptcha 成功不删可重放），见第八章。
```

**③ 前端登录态接管（对齐 login.vue afterLogin 范式）**

- token 落现有 storage 约定（与 PC 登录一致），H5 后续接口携带 `accessToken` 请求头；
- 注册成功**不跳转离开 H5**：报告页/完成页原地刷新用户态（浮条消失、CTA 变「我的积分」），`?accessToken=` 回填仅用于从 H5 跳入 PC 管理端的场景（现有 `?accessToken=` 登录串接机制三处回填对称沿用）；
- 注册成功上报 `register_success`（E05，携带 `isNewUser`，看板区分新客/老客转化）。

**④ 答卷归属迁移（claim）**

| 项 | 规则 |
| ---- | ---- |
| 问题 | 游客匿名提交的答卷 `user_id` 为空，注册后如何归户 |
| 前置缓存 | 填写页提交成功后，responseId 已入 sessionStorage 池 `pending_response_ids`（4.3.2） |
| 接口 | `POST /assessmentApi/response/claim` body: `{ responseIds: number[] }`（登录态） |
| 后端逻辑 | 批量将匿名答卷 `user_id` 补绑为当前用户：仅允许迁移**无主（user_id 为空）**答卷；单批 ≤ 20 条；时间窗限 24 小时内提交的答卷 |
| 触发时机 | quickRegister 成功回调内**静默**自动调用；失败不提示、不重试轰炸（报告页链接本身公开可用，归属迁移失败不影响浏览） |
| 防越权 | 仅本人 session 内记录的答卷可迁移；responseIds 非本人渠道提交（已有归属）一律拒绝并记日志 |

**⑤ 注册后的积分衔接（与 4.8 联动）**

```text
quickRegister 成功回调（顺序执行，每步均为独立 try）：
1. claim 迁移答卷归属（见上）
2. 调 POST /assessmentApi/points/grant 完成（4.8.2 场景 B）：
   - REGISTER_WELCOME 新人积分（isNewUser=true 才发）
   - 若 pending_response_ids 非空：补发本 session 的 ASSESSMENT_COMPLETE 积分
3. PointsToast 提示「+20 积分已到账」（见 4.8.3）
```

#### 4.3.6 我的测评（v1.1+）

- 登录用户在问星内的「我的」列表：历史答卷（测评名/结果/日期）、积分余额入口；
- 数据来源：claim 迁移后的本人答卷查询接口（survey 域按 user 查 response，现有能力）+ 现有积分余额接口；
- 游客期未注册的历史不回溯（sessionStorage 池仅存当前会话，鼓励当场注册）。

**链接模板（两种落点）**：


### 4.5 公众号后台操作闭环

> 回答用户要求：**「在公众号那边怎么操作、操作后用户发关键词/点菜单返回什么」**。v1.0 公众号侧全部走**后台原生配置人工承接**（个人未认证订阅号可完成全部动作），本系统提供「配置仓库 + 一键复制 + 同步状态追踪」，保证文案与链接不失配。

#### 4.5.1 回复规则仓库（`assessment_reply_rule`）

| 功能 | 说明 |
| ---- | ---- |
| 规则类型 | `keyword`（关键词回复）/ `welcome`（被关注回复），单表 `rule_type` 区分 |

#### 4.5.2 公众号后台操作 SOP（七步闭环）

| 步骤 | 操作位置（公众号后台） | 粘贴内容来源（本系统） | 操作后用户端返回什么 |
| ---- | ---- | ---- | ---- |

#### 4.5.4 同步状态维护（`sync_status` 状态机）

```text
                ┌──────────────── 运营点「标记已同步」(S5) ────────────────┐
                │                                                          │
   ┌───────▼────────┐   新建/编辑保存   ┌──────────────┐    停用(不改)
   │  pending 待同步  │ ──────────────→ │  synced 已同步 │ ─────────┐
   │（平台与后台失配） │ ←────────────── │（后台已生效）   │          │
   └────────────────┘   任何字段修改保存  └──────────────┘          ▼
                                              │               已停用（独立 status）
                                              │ 规则删除            （不影响后台行为）
                                              └─ 移除展示，历史事件保留 ─┘
```

| 规则 | 说明 |
| ---- | ---- |
| 单向升级 | `pending → synced` 仅允许手动标记（S5），系统不猜测后台状态；`synced → pending` 由任何编辑保存自动触发（链接变了，失配提醒） |
| 看板口径 | 心智测评中心头部展示「已生效规则数 X/Y」（synced/enabled 数）；`pending` 超 3 天的规则在管理端列表高亮提醒 |
| 非强校验 | `sync_status` 是运营约定标记，不驱动任何线上行为；失配影响仅限文案（后台发的是旧版），事件流仍按二维码/链接参数归因 |

### 4.6 埋点体系

> 回答用户要求：**「哪些地方需要进行埋点」**——给出可直接执行的全量清单（3 个 PV + 9 个事件 + 1 个预留）。

#### 4.6.1 双轨架构

现有 analytics 模块（Umami 兼容，`POST /analyticsApi/collect`）**只落 pageview，自定义事件不落库**（现状缺口），因此：

| 轨 | 承载 | 职责 |
| ---- | ---- | ---- |
| **L1 页面 PV** | analytics 模块现状（不新建） | 管「哪一页被打开」：P1～P3 三个问星页面挂载各报一次 |
| **L2 业务事件** | `assessment_event` 单表（新） | 管「哪一漏斗漏了多少」：E01～E10 带业务上下文（渠道/对象/用户） |

两轨关联键：session_id（业务侧）与 pagepath（PV 侧）在看板页面维度对齐；v1.1+ 评估 analytics 扩展事件落库后的合并方案（见 9.3）。

#### 4.6.2 全量埋点清单

**L1：页面 PV（3 处，走 `POST /analyticsApi/collect`）**

| 编号 | 页面 | 触发时机 | 携带 |
| ---- | ---- | ---- | ---- |
| P1 | 问星·测评广场 `/assessment/list` | 页面挂载 | path + query（source/refId） |
| P2 | 问星·测评填写 `/survey/fill/:shareCode` | 页面挂载 | path + query（source/refId） |
| P3 | 问星·测评报告 `/survey/result/:responseId` | 页面挂载 | path |

**L2：业务事件（9 处 + 1 预留，走 `POST /assessmentApi/event/report`）**

| 编号 | event_type | 触发位置与时机 | 关键业务字段 | 支撑指标 |
| ---- | ---- | ---- | ---- | ---- |
| E01 | `channel_visit` | 带 source 参数进入 H5（广场或填写页均可为落点） | source、ref_id、session_id、target(plaza/fill) + share_code(测评直达时) | 渠道进入量、各渠道转化分母 |
| E02 | `plaza_click` | 广场卡片点击跳转填写页前 | share_code、session_id、上游 source/ref_id | 广场点击率（E02/E01 与 P1 比较） |
| E03 | `response_complete` | 提交答卷成功后（含游客/已注册，含任意 source） | source、ref_id、session_id、share_code、response_id、user_id(有登录态时) | 测评完成量、完成率 |
| E04 | `register_show` | QuickRegisterSheet 弹层展示（报告浮条/完成页 CTA/广场入口三触发位） | session_id、trigger(float/complete/plaza) | 注册曝光与触发位效果对比 |
| E05 | `register_success` | quickRegister 成功回调 | session_id、is_new_user、trigger | 注册转化率（E05/E04）、新老客占比 |
| E06 | `guide_show` | 引导组件进入视口（IntersectionObserver） | session_id、position(complete/result) | 回流漏斗曝光 |
| E07 | `guide_click` | 引导位二维码区长按/点按 | session_id、position | 回流代理指标（E07/E06） |
| E08 | `share_click` | 分享弹窗任一渠道 Tab 点击（含海报入口） | share_code、session_id、channel(wechat/link/qr/email/poster) | 分享意愿量 |
| E09 | `poster_create` | 海报 Canvas 合成完成 | share_code、session_id、上游 source | 海报产出量；**兼直播积分幂等键**（4.8.2） |
| E10 | `follow_scan` | 带参数二维码扫码（v1.2+ 预留，仅占位不入看板） | scene 参数 | 关注归因 |

**通用字段（L2 全量携带）**：`session_id`、`user_agent`（摘要截断）、`ip_city`（城市级，不存原文）、`user_id`（可空：事件发生时已有登录态则直落，游客为空）、`created_at`。

**完整增长漏斗（事件串联，看板主视图）**：

```text

(E01)      (E02/P1)   (E03)      (E04)       (E05)      (points流水)  (E08/E09)
```

#### 4.6.3 上报接口与防刷

统一上报接口：`POST /assessmentApi/event/report`（@Public，单事件一次调用，前端 fire-and-forget 不阻塞交互）。

| 风险 | 策略 |
| ---- | ---- |
| 恶意刷新伪造进入 | 前端节流 + 后端去重：`channel_visit` 按 `session_id + source + ref_id` 三元组 5 分钟窗口仅记 1 次（Redis/内存窗口） |
| 完成量刷量 | `response_complete` 依赖真实提交接口返回的 response_id（提交侧已有去污染/限频约束），无答卷不落事件 |
| 无效 source 注入炸表 | source 白名单校验（仅收 4.4.2 枚举五值），非枚举直接拒收；refId 长度 ≤ 32、字符集校验 |
| 单会话海量事件 | 每 sessionId 60 次/分钟超出丢弃并记日志 |
| UA 抓取 | guide_click/plaza_click 等交互事件超常规速率合并计数（不逐条落库） |
| 开关影响 | `guide_enabled=false` 时前端不发 E06/E07（E01～E05、E08、E09 照常）；匿名游客的全部事件照常上报（归因与看板不依赖登录） |

### 4.8 积分联动

测评域**不自建积分能力**，复用 points 模块规则引擎（`points_rule`）与流水（`points_transaction`），仅做场景定义、种子规则与触发调用。

#### 4.8.1 规则配置（3 条种子规则）

规则随 `sql/assessment_tables.sql` 以 INSERT 种子提供，运营可在「积分管理 → 规则配置」按现有规则开关/调分（points 域 rule_code 无枚举约束，直接扩展）：

| rule_code | 场景 | 分值 | 日限/月限/终限 | 幂等键（referenceType/referenceId） |
| ---- | ---- | ---- | ---- | ---- |
| ASSESSMENT_COMPLETE | 完成一次正式测评（打卡型 quick_daily 不计） | 5 分 | 日 2 次 / 月 30 次 | survey_response / responseId |
| ASSESSMENT_POSTER | 生成测评海报（分享图制作成功） | 5 分 | 日 3 次 / 月 20 次 | assessment_event / E09 事件 id |
| REGISTER_WELCOME | 注册成功即奖（恒定欢迎分） | 20 分 | 终身 1 次 | user / userId |

- 三个场景均**不发券**，走纯积分（calcMethod=FIXED，见积分 PRD 4.2 计算方式）。
- REGISTER_WELCOME 由注册链路触发，天然归属 quickRegister 后置流程；若该规则被运营关闭，quickRegister 处跳过发放。
- 幂等约束由发放接口统一实现（4.8.2），规则表不承载去重。

#### 4.8.2 发放时机与幂等

**统一发放接口**：`POST /assessmentApi/points/grant`（登录态），入参 `{scenario, responseId?, eventId?}`，内部按上表组装 referenceType/referenceId 后调用 points 域 `operatePoints`（points.service.ts:824-840）。

| 场景 | 触发时机 | 前置判断 |
| ---- | ---- | ---- |
| A：已登录用户完成测评 | 提交接口成功返回后，**前端直调 grant**（fire-and-forget，不阻塞报告页） | responseId 有主（user_id 已绑定）即发 ASSESSMENT_COMPLETE |
| A'：已登录用户生成海报 | 海报绘制完成回调内直调 grant | eventId 取 E09 落库返回的事件 id |
| B：游客补领（游客答卷 → 注册后） | claim 成功的注册回调内，后端按 `pending_response_ids` 逐笔补调 grant | 仅迁移成功的答卷补发；游客未注册/未 claim 的答卷**不补发**（防刷：避免无限期追溯发分） |
| C：注册欢迎分 | quickRegister 建号成功后置流程内直接发放 | `isNewUser=true` 才发；已存在用户登录不发 |

**幂等实现**（参照 task.service.ts:906-914 的 `pointsTransaction.findFirst` 范式）：

```text
grant(scenario, ref):
  1. key = (rule_code, referenceType, referenceId)
  2. 已存在同 key 流水 → 直接返回成功（幂等）
  3. 校验日/月/终限额（现流水计数）
  4. operatePoints({ userId, rule, change: +分值, referenceType, referenceId })
```

- 并发兜底：`points_transaction` 加唯一索引 `uniq_rule_ref(rule_code, reference_type, reference_id)`，插入冲突按已发放处理。
- 发放失败不回滚测评主流程，仅记日志，看板「注册→领分率」暴露漏发。

#### 4.8.3 H5 端积分呈现

| 项 | 约定 |
| ---- | ---- |
| 到账反馈 | 复用 H5 积分 Toast 组件（PointsToast）：文案「+5 问星积分已到账」，出现在报告页右下角 2.5s 自动消失 |
| 游客态文案 | 游客完成测评提示「积分已为您暂存，注册登录后自动补发」，引导其完成 E04→E05 |
| 补领反馈 | 场景 B 补发成功时 Toast「检测到您的历史测评，+N 积分已补发」（N=补发笔数×单笔分值） |
| 积分明细 | 用户可在「我的积分」流水页看到 source=测评 的三类记录（复用现有流水页，无需改造） |
| Mock 注记 | 前端若 `VITE_POINTS_MOCK=true`（积分域现存的本地 Mock 开关），则积分 Toast 走前端假发放，不调 grant——上测试环境需关闭 |

### 4.9 公众号服务端对接（v1.1+）

v1.0 的「回复内容 + 链接」由运营在公众号后台手工粘贴；v1.1 接入服务端对接后，实现**规则库一键下发**，消灭手工同步。两模式并存，逐条切换。

#### 4.9.1 对接准备

| 项 | 约定 |
| ---- | ---- |
| 凭证存储 | 复用 app-info 域：app_info 新增 app_name='wechat_oa' 记录，app_id/app_secret 存入其凭证字段（沿用现有加密与权限约束，运营在「应用管理」维护） |
| access_token | 定时任务（Redis 缓存，key=`wechat_oa:access_token`，提前 5 分钟刷新），全局单例复用，不复用按用户 token 的体系 |
| 回调接入 | 网关新增 `GET /api/public/wechat-oa/callback`（验签 echostr 接入校验）与 `POST /api/public/wechat-oa/callback`（XML 消息体），@Public + IP 白名单 |
| 消息处理器 | 建注册表 `Map<MsgType|Event, Handler>`：subscribe（下发欢迎语） / text（关键词匹配 reply 规则） / CLICK（菜单事件映射） / unsubscribe（记录沉淀） |

#### 4.9.2 规则一键下发与并存

| 项 | 约定 |
| ---- | ---- |
| 一键下发 | OA 配置页新增「下发到公众号」按钮：将 sync_status=pending 的回复规则+自定义菜单打包调用公众号接口；成功回调后置 synced |
| 菜单引擎 | S4 菜单树调用「自定义菜单创建接口」，按钮仍为 click 发文字类型（订阅号能力面），响应内容从回复规则仓库取 |
| 失败回滚 | 下发接口返回 errcode≠0 时整批回退 pending，页面展示公众号侧错误码与中文翻译对照表 |
| 并存过渡 | 逐条切换：任一规则 synced 即服务端托管；仍为 pending 的规则继续用手工 SOP（4.5.2）；运营可单条「下线托管」恢复手工 |

> 本节接口均为 v1.1+，随版本排期启动后细化参数；v1.0 不开放任何服务端下发入口。

### 4.10 认证后高级能力（v1.2+）

以公众号完成「微信认证」为前提解锁，接口属公众号对接域（见 7.6）：

| 能力 | 说明 | 与测评域联动 |
| ---- | ---- | ---- |
| 网页授权 OAuth | `/api/public/wechat-oa/oauth` 静默 snsapi_base换取 openid，登录页可「微信一键登录」（沿用 registerByOauth 的 OAuth 建号范式，userService.ts:257-284） | 渠道兜底注册转化率（替代/并列验证码注册） |
| 模板消息 | 对接 notify 模块：测评报告生成通知、积分到账提醒（模板由运营在公众号后台申请后填模板 ID 进 notify 配置） | 完成→回访召回 |
| 带参二维码 | 渠道生成专属 scene 二维码，subscribe 事件解析 scene 触发 E10 归因 | 关注即进入，归因到具体海报/地推物料 |
| JS-SDK | `/api/public/wechat-oa/js-signature`（wx.config），扫码/分享卡自定义 | 问星 H5 分享卡片置灰尾自定义标题缩略图，提升回流率 |
| 菜单高级接口 | 认证号可建「跳转网页」型菜单按钮，直接开 H5 广场 | S4 菜单树可升级一档（view 型直达 `/assessment/list`），仍保留 click 发文字兼容未认证场景 |

> v1.2+ 能力不影响 v1.0/v1.1 版本本身验收；带参二维码的 E10 事件已在 4.6.2 占位。

### 8.1 存量安全机制整改清单（随本版关联整改）

调研发现的既有后台安全隐患，本版关联修两处，同步知会运维侧跟进：

| # | 问题 | 影响 | 处置 | 版本 |
| ---- | ---- | ---- | ---- | ---- |
| 1 | 兑换验证码成功后未删除记录，同一验证码可重放注册 | quickRegister 无法成立，注册即可被盗刷 | 本次随本版改造：验证码校验通过即消费（删除或置 used），quickRegister 依赖一次性 | v1.0 |
| 2 | `POST /points/operate` 类直发接口无 @RequirePermissions 也不校验调用方，body 可能携带 userId | 任意登录态用户更动任意账户积分 | grant 封装层强制服务内部调用，不从路由暴露；operate 路由补权限装饰器或收紧为内部 service-only；禁止 body 传 userId（统一读 accessToken 解析） | v1.0 |
| 3 | registerByPhone 现无验证码强校验 | 同上类似，原生注册接口也可盗刷 | v1.0 顺带补强校验；quickRegister 封装路径必前置验证码 | v1.0 |
| 4 | 密码保存明文（全局项） | 全线账户安全风险 | 非本域范围，登记移交安全整改专项；本版不动 auth 域既有逻辑 | 后置 |

### 8.2 灰度与发布方案（v1.0）

本需求直接面向 C 端并承担注册与积分发放，**需灰度发布**，按「单渠道 → 渠道铺开 → 全量」三段推进（D1 = 灰度首日）：

| 阶段 | 时间窗 | 灰度范围 | 进入条件（全部满足才推进下一段） | 重点监控 |
| ---- | ---- | ---- | ---- | ---- |
| **R1 单渠道灰度** | D1–D7 | 仅 keyword 渠道单规则（蓝本「每日智慧」打卡，4.5.3）；article / welcome / menu 渠道暂不铺设 | ① ≥3 款测评上架并通过四项校验（4.1.4）；② 8.1#1 验证码一次性消费整改上线；③ 8.3 各风险控制项确认生效 | E01–E03 正常落量；验证码接口异常率 <1%；grant 幂等冲突数 = 0 |
| **R2 渠道铺开** | D8–D21 | S1–S4 方案全量铺设（article / keyword / welcome / menu，见 4.5.2/4.5.3），四渠道全部放开 | R1 期 L3/L1 ≥ 10%（4.7.1 口径）且零告警 | E05/E04 ≥ 5%（注册转化爬坡）；积分日月终限额无触顶；异常/刷量 session 占比 < 3‰ |
| **R3 全量** | D22 起 | 全渠道常态运营；**T0 = D22** | R2 连续 7 日无告警；数据看板（4.7，P1 项）已交付上线 | 转入看板常态监控（4.7）；T0+90d 按 1.4.3 验收 G1–G5，未达标项进入 v1.1 复盘 |

**回滚与止血开关**（全部为配置级操作，不依赖发版）：

| 风险场景 | 止血操作 | 配置入口 |
| ---- | ---- | ---- |
| 引导位文案事故 | `guide_enabled=false` 一键隐藏 C 端三处引导位 | 4.4.1 引导位配置 |
| 单款测评内容风险 | 下架该测评：广场即刻隐藏、直链进入填写页拦截 | 4.1.4 测评上架管理 |
| 渠道回复文案事故 | 停用对应 reply_rule，并同步删除公众号后台该关键词配置 | 4.5.1 回复规则仓库 |
| 积分超发/盗刷 | 停用对应积分规则（即时生效；已发流水不回冲，事后人工对账清理） | 4.8.1 积分规则配置 |
| 验证码接口被刷 | 收紧 loginApi 验证码频控参数（Redis TTL / 次数阈值） | 登录域既有配置 |

> **v1.0 不做 ABtest**：analytics 侧当前仅页面 PV 落库、无对照组分流基建（4.6.1），灰度评估以「渠道分期时间序列对比」替代，分流实验基建待 v1.1+ 评估后立项。

### 8.3 风险与合规披露

**① 资金风险判断**

| 项 | 结论 |
| ---- | ---- |
| 是否跟钱相关 | **否**——不发券、不涉现金提现，积分不可兑现、不可转让（4.8） |
| 资金损失风险等级 | **中**——积分可兑换站内权益，超发/盗刷构成权益损失敞口 |
| 控制项 | 发放幂等三方键 + `uniq_rule_ref` 唯一索引（4.8.2）；积分日月终限额（4.8.1）；验证码一次性消费（8.1#1）；claim 仅迁移无主答卷并做越权校验（4.3.5） |
| 残余风险与放量门槛 | 8.1#2 积分直发接口越权必须随版整改完成，未完成不得进入 R3 全量（8.2） |

**② 数据泄露风险**

| 项 | 结论 |
| ---- | ---- |
| 有无数据泄露风险 | **有，风险等级：低** |
| 收集范围 | 仅 quickRegister 收集手机号（复用登录域既有字段）；事件流全脱敏——IP 仅存城市级、UA 摘要截断、不存微信号/openid（第八章 #6） |
| 存储与传输 | 手机号沿用用户体系既有存储策略；验证码 Redis 120s TTL 一次性消费；公开接口全 HTTPS；管理域 `@RequirePermissions` 全覆盖（第八章 #7） |
| 风控沟通结论 | 个人项目无外部法务/风控环节，以上判断由 PM 自审并在灰度评审留痕；密码明文存量问题（8.1#4）登记移交专项、不改变本版结论；本节控制项生效确认列为 R1 进入条件（8.2） |

**③ 内容与平台合规**

| 风险 | 边界红线 | 落点 |
| ---- | ---- | ---- |
| 心理测评表述边界 | 严禁「诊断 / 抑郁症 / 治疗 / 康复」等医疗临床表述；产品定位为娱乐与自我探索，报告语义仅用「倾向 / 原型 / 能量」等描述词 | 报告页固定免责脚注「测评结果仅供娱乐参考，不构成医学诊断或专业心理评估」（4.2.2，前端常量、不可配置关闭） |
| 周易题材表述边界 | 限人格意象 / 原型表述；严禁「改运 / 转运 / 消灾 / 付费化解」等迷信营销词 | 类型库预置模板（4.1.1）与运营自建文案同受约束；违规文案即时经规则仓库改写重发（4.5.1） |
| 未成年人保护 | 无年龄门槛，但内容无不适成分、纯虚拟积分不涉真实消费 | 商业化（权益兑换实物 / 付费测评）启动前补做年龄与消费合规评估 |
| 短信验证码 | 复用登录域既有短信通道与合规策略 | 无新增合规义务 |

**④ 披露结论**：无直接资金风险（不跟钱）；数据泄露风险低、内容合规风险低-中，全部控制项随 v1.0 版本交付，并逐一列入 8.2 灰度各阶段进入条件，逐段复核后放量。
