# drawStars 需求文档（PRD）输出规范

> **适用范围**: drawStars 平台各业务模块产品需求设计文档  
> **参考样例**: `问卷管理系统_PRD_v1.0.md`  
> **版本**: v1.0  
> **日期**: 2026-08-06  

---

## 一、文档定位

PRD 面向产品、研发、测试，用于约定「做什么、做到什么程度、如何验收」，而非实现细节教程。

| 读者 | 关注点 |
|------|--------|
| 产品 | 目标、范围、优先级、版本规划 |
| 前端/后端 | 功能规则、数据模型、接口、扩展点 |
| 测试 | 角色权限、状态流转、边界与异常 |

---

## 二、文件与命名

| 项 | 规范 |
|----|------|
| 存放目录 | 仓库根目录 `prd/` |
| 文件名 | `{模块中文名}_PRD_v{主版本}.{次版本}.md` |
| 示例 | `问卷管理系统_PRD_v1.0.md`、`积分管理体系_PRD_v1.0.md`、`权限管理体系_PRD_v1.0.md`、`日志管理体系_PRD_v1.0.md` |
| 编码 | UTF-8（无 BOM） |
| 语言 | 简体中文为主；枚举值/接口路径可用英文 |

文档头部元信息（标题下引用块）必填：

```markdown
> **项目**: drawStars (Vue3)  
> **版本**: v1.0  
> **日期**: YYYY-MM-DD  
> **状态**: 初稿 / 补充更新（说明变更点） / 已评审
```

---

## 三、章节结构（固定顺序）

完整 PRD **应按下列十章 + 附录** 组织。某章确实无内容时保留标题，写「本期不适用」并说明原因，禁止随意删章导致编号错乱。

| 章 | 标题 | 必备 | 说明 |
|----|------|------|------|
| 一 | 需求背景与目标 | 是 | 背景、设计目标表、不在本期范围 |
| 二 | 用户角色 | 是 | 角色 × 诉求；与 RBAC 权限点对应 |
| 三 | 功能模块总览 | 是 | 树状模块图（代码块） |
| 四 | 各模块详细设计 | 是 | 核心篇幅：功能表、规则、状态机、配置项 |
| 五 | 核心数据模型 | 是 | ER 示意 + 实体字段表 |
| 六 | 页面结构 | 是 | 路由规划 + 关键页面布局说明 |
| 七 | 接口概要 | 是 | 按域分组的 API 清单 |
| 八 | 非功能性需求 | 是 | 性能/并发/兼容/安全/可用性等 |
| 九 | 扩展性设计 | 是 | 扩展点、策略/注册模式、现有系统集成 |
| 十 | 版本规划 | 是 | 分版本范围与周期 |
| 附录 A | 术语表 | 是 | 业务术语统一定义 |
| 附录 B | 竞品/参考（可选） | 否 | 可借鉴点一览 |

## 四、各章写作细则

### 4.1 需求背景与目标

- **背景**：说明平台现状缺口与业务场景（条列）
- **设计目标**：用表格（目标 | 说明），目标宜短词（易用/灵活/可扩展/安全等）
- **不在本期范围**：明确砍掉的能力，避免范围蔓延

### 4.2 用户角色

| 列 | 要求 |
|----|------|
| 角色 | 与系统实际角色/权限一致 |
| 说明 | 一句话职责 |
| 核心诉求 | 该角色最关心的 1～3 点 |

文末注明权限码（如 `system:points:list`）与菜单/按钮控制方式。

### 4.3 功能模块总览

使用缩进树（Markdown 代码块），模块编号与第四章小节对应，便于检索。

### 4.4 各模块详细设计（核心）

按模块拆 `### 4.x`，子能力用 `#### 4.x.y`。优先使用：

| 表达形式 | 适用场景 |
|----------|----------|
| 功能表（功能 \| 说明） | CRUD、配置项、操作能力 |
| 状态机（ASCII / 表格） | 生命周期、账户状态、交易状态 |
| JSON / 伪代码片段 | 配置结构、规则条件→动作 |
| 策略表 | 防刷、限额、计算方式、权益 |
| 开关行为说明 | 开启/关闭对 UI 与数据的影响 |

要求：

- 写清**业务规则与边界**（上限、幂等、必填、权限），少写「实现用什么框架」
- 已实现能力与规划能力区分：规划项标注版本（如 `v1.1+`）
- 与代码不一致时，以「目标态」写清，并在状态元信息中标注「待对齐」

### 4.5 核心数据模型

1. ASCII ER 图（1:N / N:1）
2. 每张核心表：字段 | 类型 | 说明
3. JSON 字段约定单独说明（如 `answer_data`、`benefits`）
4. 字段命名与库表可对齐 snake_case；接口层可说明 camelCase 映射

### 4.6 页面结构

1. **路由规划**：完整 path 树
2. **关键页面**：布局分区、主操作、空态/权限提示要点
3. 管理端与 C 端（个人中心）分开写

### 4.7 接口概要

按业务域分小节，表格列：**接口 | 方法 | 说明**。

- 路径以实际网关为准（如 `/api/points/...`）
- 写清权限要求、关键入参约束（可在说明列简述）
- 不替代完整 OpenAPI；复杂体可在第四章用 JSON 示例补充

### 4.8 非功能性需求

至少覆盖：性能、并发、兼容性、数据安全、可用性；按模块需要可加国际化、大数据策略等。指标尽量可量化。

### 4.9 扩展性设计

说明可插拔点（注册表/策略/适配器）、新增能力时的步骤，以及与用户、权限、通知、日志等现有模块的集成表。

### 4.10 版本规划

| 版本 | 范围 | 预计周期 |
|------|------|----------|

范围与「不在本期范围」、第四章 `v1.x+` 标注保持一致。

### 4.11 附录

- **术语表**：中英对照 + 一句话定义
- **竞品参考**（可选）：产品 | 可借鉴点

## 五、格式与文风约定

1. **标题层级**：`#` 文档名 → `##` 章 → `###` 模块 → `####` 子能力
2. **强调**：关键约束用加粗；避免整段加粗
3. **表格优先**：枚举、配置、对比一律用表，少用长段落
4. **引用块**：设计原则、开关说明、存储约定等用 `>`
5. **代码块**：树形结构、状态机、JSON、接口伪代码
6. **版本标记**：`（v1.1+）`、`本期仅支持…`、`预留`
7. **禁止**：大段无结构散文；只贴源码不写规则；臆造未对齐的接口字段且不标注

## 六、与代码对齐原则

撰写或修订 PRD 时建议对照：

| 类型 | 对照位置（示例） |
|------|------------------|
| 类型/枚举 | `src/types/{module}.ts` |
| 前端 API | `src/api/{module}.ts` |
| 页面路由 | `src/router/**` |
| 管理端页面 | `src/views/manage/**` |
| 后端接口 | serve 仓库 `src/nest/modules/{module}/` |
| 表结构 | `sql/{module}_tables.sql` / Prisma schema |

对齐策略：

- **已上线行为**：按代码事实写清规则（含限额、权限码、流水字段）
- **规划能力**：单独标注版本，勿与已实现混为一谈
- **Mock 与真实**：若存在 `VITE_*_MOCK`，在接口章或附录注明切换方式

- [ ] 角色与权限码可落地
- [ ] 模块树与第四章、路由、接口可互相索引
- [ ] 状态流转与字段枚举无矛盾
- [ ] 「不在本期范围」与版本规划一致
- [ ] 术语表覆盖正文首次出现的核心概念
- [ ] 文件名、路径符合本规范
